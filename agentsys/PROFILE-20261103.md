# Phase A profile: where agent wall time goes (Hermes, 45 days to 2026-11-03)

Source: every Hermes `state.db` on groot (default, clean, chiefstaff, intake, rippletern), read-only.
204,278 tool results, 130,001 model turns, ~15k sessions (50% of tool rows are subagent sessions).
Raw output: `receipts/profile-hermes-45d-20261103.txt`. Re-run: `extract_hermes.py` then `analyze.py`, `discovery.py`.

Timing proxy (Hermes stores one timestamp per message, written when the message completes):
- `exec_s` = tool result ts − parent assistant ts (tool wall time, including harness overhead and approvals).
- `think_s` = parent assistant ts − previous message ts (the model turn that produced the call).
Sanity check: `memory` p50 0.05 s, `read_file` p50 0.18 s, so the floor is the harness, not the clock.
Not yet covered: OMP, Claude Code, Codex (AgentsView has 1.05M tool calls but only ~3.4k carry
execution timestamps; see Track E0), GPU/CPU host metrics (no history store exists: k3s has only
metrics-server, no Prometheus).

## 1. The model turn is the unit of cost, not the tool

| | hours | per-unit p50 |
|---|---:|---:|
| Model turns (think) | 606 | 8.1 s (p90 32 s) |
| Tool execution | 579 | 0.2–1 s for search/read tools |

A `rg` vs `grep` choice is ~10 ms (hyperfine, `receipts/startup-groot-20261103.json`: rg 5.9 ms,
grep -r 17.7 ms, git grep 8.5 ms, fd 4.8 ms, find 0.9 ms; node/Go CLIs qmd 116 ms, gh 108 ms).
One avoided turn is ~8,000 ms. **Engine and startup speed are 2–3 orders of magnitude below the turn
cost, so they are not worth optimizing for interactive work.** They matter only inside loops that
call a tool thousands of times, and in unscoped searches (tails, below).

Turn time by model (session model): Opus 5.5 p50 6.4 s, Sol 6.1 8.2 s, Astra 13.1 s
(p90 47 s). Model choice is the semantic router's job and stays a separate Pareto decision.

## 2. Ranked bottlenecks (Amdahl order)

| # | Bottleneck | Evidence | Hours/45d | Lever |
|---|---|---|---:|---|
| 1 | Discovery turns: agent doesn't know where to look | 31% of turns are pure search/read; 25% of wall time | 282 | locator memory + toolkit card |
| 2 | Blocking waits in the foreground | terminal commands with `sleep`: 4,816 calls, p50 20 s, p90 280 s; `process_manage` waits p90 180 s | 105 + 71 | event-driven waits (background + notify), law in shadow mode |
| 3 | Single-call turns | 53% of tool results came from turns with one call | (inside #1) | batching rule in the card |
| 4 | Empty search → search again | 3,805 near-empty search results; 2,534 (67%) followed by another search | (inside #1) | "if empty, next place to look" table |
| 5 | Long discovery runs | 1,795 runs of ≥5 consecutive search turns (92 h); 341 runs ≥10 (37 h) | 92 | eval-set source (see Track A) |
| 6 | Slow history search | `mcp__ctx__search` p50 46 s, p90 183 s (215 calls) vs `session_search` p50 0.28 s, `z0_file_search` p50 0.77 s | 4 | fix or demote ctx in the card |
| 7 | Unscoped searches | `fd` p90 300 s (timeouts), `grep` small-result p90 35 s, roots `/`, `/mnt/zer0models`, `~` | ~10 | scoped roots / fff index |
| 8 | Waiting on the owner | `clarify` 18.9 h | — | not slowness; exclude |

## 3. What this says about the parameters worth optimizing

- Worth it: turns per task, turns spent locating, empty-retry rate, blocking-wait hours, tail
  latency of a handful of tools (ctx search, unscoped fd/grep).
- Not worth it (record as null results, don't build): swapping grep→rg for small searches,
  CLI cold-start, Rust rewrites of tools whose p50 is under the 0.17 s harness floor.
- Search result size barely moves p50 (rg <2k results 0.34 s, ≥20k 1.26 s), so result-size
  slicing only matters for context cost (tokens), not wall time.
